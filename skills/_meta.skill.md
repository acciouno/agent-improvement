# Skill: _meta

> Authoring policy for future skills. This skill governs how new skills get
> made — the paper's "meta-skill steering how future skills are authored."
> A template describes format; this describes policy: when to create, when
> to extend, when to refuse.

**Version:** n/a — git is the version history.

## Purpose

Keep the skill library small, non-overlapping, and evidence-backed.

## Trigger conditions

- Before drafting any new skill or proposing one.

## Procedure

1. Search existing skills first: can one absorb this change? A new-skill
   proposal must argue why not (the template requires it).
2. One skill, one job. If the draft needs "and also," split it.
3. Every template section must be fillable *now* — especially Provenance
   (real evidence, not "seems useful") and Known limits.
4. Prefer filtering or editing an existing skill over rewriting from a task
   outcome. Evidence over enthusiasm.
5. Count the cap: at most 12 active skills. A new skill displaces an
   incumbent or justifies growing the cap — the human decides.

## Depends on / conflicts with

- None. This skill constrains all future skills **on authoring-process
  questions** (when to create / extend / refuse, cap discipline) — conflicts
  on process resolve in its favor. It does not override domain skills inside
  their own domain: e.g. date-verification wins any conflict about whether a
  date is "probably fine." If the two ever genuinely overlap, the narrower
  domain claim wins and the overlap is flagged for cleanup per guideline 8.

## How to tell it's working

- New-skill proposals cite the absorb-argument; none are approved without it.
- Active skill count stays within cap; the registry has no overlapping triggers.

## Intended executor

Any agent working in this repo.
